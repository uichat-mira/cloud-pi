### 2. Coding Agent 的评测盲区：把“能改”当成“改对了”（窗口外，一手论文，作为背景）

arXiv 2610.40269《When Modernization Breaks Working Code: A Single-File Study of LLMs on Legacy PHP》，v1 提交于 **2026-10-29 15:29 UTC**——**超出 48h 窗口约 4 天**，按规则仅作背景，但因与 Agent 工程质量直接相关，建议保留 [S20]。

- 实验设计：5 个 LLM，各自把 100 个 WordPress 4.0 的 PHP 文件现代化到 PHP 8.3，要求**行为保持不变**，且**不给项目上下文、不给执行反馈**；用 630 项隐藏行为检查与 511 条 Rector 检出的现代化问题来评估 [S20]。
- 关键反直觉结果：**不动手是最好的基线之一**——83 个文件原样即通过全部检查；表现最好的模型改完后只剩 59 个通过 [S20]。
- 破坏与修复严重不对称：每个模型平均**弄坏 32–51 个原本可用的文件**，最多只修好 10 个；规则工具 Rector 弄坏 7 个、修好 6 个 [S20]。
- 大部分破坏是**不必要的**：511 条检出中仅 37 条（7%）在 PHP 8.3 下确实需要修改；而在“本不需要改”的兼容文件里，模型弄坏的比例达 **36–60%**，Rector 为 8% [S20]。
- 失效机理值得工程团队记录：多数回归来自**文件改完根本无法加载**，常见原因是模型写出了 PHP 自身拒绝的类型声明；作者强调这类错误**不需要项目上下文就能避免** [S20]。
- 论文的方法论主张：LLM 现代化评测**必须设置“不改动”基线，并把“现代化程度”与“行为保持”分开报告** [S20]。

**推断**：这条对《见π》的实用价值高于任何单次模型发布——它说明当前 coding agent 的“重构/升级”类任务在高自主度、无反馈闭环下**期望值为负**，产品侧更稳妥的设计是“先给出不需要改的证据，再谈改”。

### 3. Agent 身份层：密码学身份从提案变成可构建的库（时间不明，一手仓库）

GitHub 仓库 `arkenforge/arken-core` [S12]：

- 定位为 ArkenForge 生态的 **Rust 加密核心**，负责三件事：生成带 60 秒 TTL 的随机 nonce 挑战、用 **ECDSA secp256k1（经 ethers-rs）** 验签、按 W3C 规范解析 **did:key** 身份（secp256k1 对应 `zQ3s…` 前缀）[S12]。
- 交互模型：未签名请求收到 401 与一次性 nonce → 客户端用私钥签名后携带 `Authorization: Signature` 重试 → 服务端验签并返回该 Agent 的 did:key；**服务端不存储任何会话状态** [S12]。
- 身份语义：同一密钥对在所有运行 Arken 的服务端上得到**同一个 DID**，即“一个身份，所有工具” [S12]。
- 生态分层清晰：`arken-auth`（Express/FastAPI 中间件、客户端 SDK、MCP 集成）、`arken-registry`（发现接受 Arken 鉴权的 API）、`arken-verifier`（托管验签，按量计费）[S12]。
- **项目自我披露的局限**（这部分比功能更值得引用）：明确标注**未达生产可用**；nonce 存于内存，重启或多实例部署会失效；**无私钥恢复**；需要 Rust 工具链，预编译二进制在 1.0 路线图上 [S12]。
