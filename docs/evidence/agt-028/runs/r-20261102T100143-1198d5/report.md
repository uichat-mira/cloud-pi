# 《见π》AI Agent 工程进展速览（最近 48h）

## 摘要

- 在 48 小时窗口内，最实质的一份工程证据是一份以“同一个模型、不同 Agent”为控制变量的 MCP 可用性测评：Claude Haiku 5.5 分别经 OpenCode 与 Claude Code 调用同一批 21 个 MCP Server，成功率分别为 82.0% 与 65.4%，差距集中在“Agent 自带工具与 Server 功能重叠”的场景 [S13]。
- 该测评给出的核心工程结论是：MCP Server 的“可用性”不是 Server 的固有属性，而取决于调用它的 Agent；同一 Server、同一模型、同一任务可以在一端得 96%、在另一端得 11% [S13]。
- 更值得注意的反而是“忽略率”：在理应调用 Server 的试验中，Codex 跳过 Server 的比例达 44.5%，Claude Code 为 36.5%，OpenCode 仅 16.1% [S13]。这说明 Agent 的“自带工具优先”策略会系统性地遮蔽生态里的工具。
- 一项多智能体提示词优化框架 CEPO 于 arXiv 上线，其摘要称在 11 个基准上对 4 种既有优化器均有一致提升 [S2]；但页面显示实际投稿时间为 2026-10-26，**超出 48h 窗口，仅作背景** [S2]。
- 面向 Agent 的身份与鉴权层出现早期实验（Arken：用 `did:key`＋ECDSA 签名替代密码/会话访问 MCP Server 与 API），但仓库自述“not production-ready”，日期不可核 [S9]。

## 关键进展

### 1. MCP 生态的评测视角从“Server 好不好”转向“Agent 会不会用”

SineFrame M3 于 2026-11-01 发布测评（页面元数据可核验）[S13]，方法要点：

- 固定模型为 `claude-haiku-5-5`，对比 Claude Code 2.1.312 与 OpenCode 1.19.5；另加 Codex 0.165.0（跑 `gpt-6-luna`，因此 Codex 一列是“Agent＋模型”的合并对比，不构成纯 Agent 对照）[S13]。
- 21 个真实 MCP Server，每台约 20 个任务，7 种任务形态，每任务 3 次试验，共 3,717 次计分试验；试验区间为 2026-10-29 至 2026-11-01 [S13]。
- 计分口径很关键：一次试验算成功，需要“答案正确”**且**“关键值出现在该次试验中此前的 Server 响应里” [S13]。也就是说，它度量的是“Server 是否被用上”，而非“用户问题是否被解决”。

结果（同模型、仅换 Agent）[S13]：

| Server 分组 | Claude Code | OpenCode | Codex |
|---|---|---|---|
| 11 个与内置工具无重叠 | 93.5% | 96.2% | 92.1% |
| 10 个与内置工具重叠 | 34.5% | 66.3% | 17.2% |
| 全部 21 个 | 65.4% | 82.0% | 56.5% |

- 在无重叠组，三者差距仅 4.1 个百分点；在重叠组，Claude Code 落后 OpenCode 32 点、Codex 落后 49 点 [S13]。**推断**：该分布说明差距主要来自“工具选择/路由”而非“工具调用能力”。
- 忽略率（应当调用却未调用）：Codex 44.5%、Claude Code 36.5%、OpenCode 16.1% [S13]。
- 归因证据：在 10 个重叠 Server 上，Claude Code 有 378 次试验是通过自家工具作答，其中 342 次答对；它会转向 `WebSearch`/`WebFetch`，在 Memory Server 上则常直接打开本地 `MEMORY.md` [S13]。Codex 在 Microsoft Learn、Terraform、DeepWiki、Exa 上“一次都没调用 Server” [S13]。
- OpenCode 的优势带有结构性原因：在 1,239 次试验中它从未调用内置网页搜索，只有 `webfetch`，因此在 Exa 上得 96%，另两者仅 11% [S13]。

作者对 Server 作者的建议是操作性的：上线前应“按用户实际使用的 Agent 分别测试”，并在报告成功率的同时报告忽略率——低成功率＋高忽略率意味着“没被问”，低成功率＋低忽略率才意味着“问了但出错” [S13]。

**推断（非来源结论）**：这构成对 MCP 生态的一个结构性压力——Server 不仅与其他 Server 竞争，还要与宿主 Agent 的原生工具竞争；对 Agent 厂商而言，“优先用自家工具”在用户侧往往是正确行为（S13 自己也承认这一点），但对开放工具生态是负外部性。这与“Agent 平台化、工具内化”的趋势一致，但该趋势判断本身**待核**。

### 2. 多智能体提示词优化：协调层与执行层解耦（背景，超出窗口）

CEPO（Coordinator-Executor Prompt Optimization）将 MAS 的提示词拆成“共享的 coordinator 提示词”与“各 agent 专属的 executor 提示词”，按角色分别更新，底层搜索仍交给既有优化器 [S2]。摘要称覆盖 4 个领域 11 个基准，对 4 种既有优化器均有一致提升，并在文档理解 MAS 上显示优化预算效率与“随 agent 数量扩展”的改善 [S2]。

需要标注的是： arXiv 页面投稿历史为 `Mon, 26 Oct 2026`，**不在 48h 窗口内**，此处仅作为背景脉络引用 [S2]。

### 3. Agent 身份与鉴权：早期实验，尚不可用于生产

Arken 的 `arken-core`：以 `did:key`（secp256k1，W3C DID 规范）标识 Agent 身份，请求先收到 401＋一次性 nonce（60s TTL），客户端用私钥签名后带 `Authorization: Signature` 重试，服务端验签并返回该 Agent 的 DID；设计目标是“无密码、无会话、无可泄露存储” [S9]。其上层包含 `arken-auth`（Express/FastAPI 中间件、客户端 SDK、MCP 集成）与发现注册表 [S9]。

仓库自陈的限制很明确：**非生产可用**，nonce 存于内存（重启或多实例即失效，需共享存储）、无密钥恢复、需 Rust 工具链 [S9]。该仓库页面**未标注发布日期**，无法判断是否落在 48h 窗口内，按背景处理 [S9]。
