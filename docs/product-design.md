# Mira Cloud Agent · 产品设计 v0.2

> **状态：产品方向与用户决策（更新于 2026-11-05）；具体能力和验收以当前运行代码、部署与 Live 证据为准。**
>
> 这是本仓库产品边界与用户决定的单一真相源。详细权限/接口与运行架构尚未冻结时要显式标识，不把候选实现写成产品承诺。

## 1. 定位

**Mira Cloud Agent 是一只长期运行、可主动工作、可通过 IM 双向协作的轻量 Agent。** 它以 Pi 为首选内核，服务于定时研究和日常委托，作为 Hermes Agent 的实用替代品及未来云 Mira 的前身。不是远控工具、DC 控制台、Mira Desktop 云端复制品，也不是完整 Agent 平台。

第一版优先验证和交付三个结果：**到点研究有成果、观澜新闻可被安全读取、飞书聊天真的能够委托 Agent 工作**。原生 MCP 是基础连接能力，不是第四套自建平台。

## 2. 用户已确认的 V1 产品决定

| 主题 | 已确认决定 |
| --- | --- |
| 执行内核 | **Pi SDK 优先**；优先复用官方/成熟插件，缺口才做薄适配 |
| 研究 | 支持可配置、可暂停、可立即执行的定时研究；也支持聊天临时研究 |
| 管理入口 | **Mira Cloud Auth 的 /account/services** 增加 Cloud Agent 服务入口与控制台 |
| 任务配置 | 在控制台创建、修改、暂停、删除、查看历史；**V1 不要求飞书自然语言修改计划** |
| 投递目标 | **每个任务独立指定一个或多个飞书/企业微信个人或群聊目标**，必须使用可信目标配置，不由群消息或模型决定收件人 |
| 双 IM 聊天 | 飞书、企业微信均支持平台可投递的**任意用户私聊**；群内**任何成员明确 @ 机器人**即可交互，不因用户/群白名单被拒绝；非 @ 群消息不触发回答 |
| 聊天准入 | **平台负责谁能接触机器人**；Cloud Pi 不额外维护用户 ID、群 ID 白名单，不校验是否属于某个授权群，也不因离群撤销私聊资格。平台送达及 @ 判断仍须真实可靠 |
| 权限边界 | **聊天开放 ≠ 维护者权限开放**。管理员任务/配置由 Cloud Auth 校验；Guanlan 私有订阅、消费账本及任何私有或可变更数据的 MCP 工具，必须按可信身份/委托单独授权；不允许公开聊天继承维护者委托凭证 |
| 观澜 | Mira Cloud Account **内建新闻服务**；MCP 是调用协议，不要求用户另行登录、OAuth 同意或粘贴 Token |
| MCP | 首选 **Pi 原生 MCP Extension**；支持本地 stdio 与远程 Streamable HTTP；按任务收窄工具及权限 |
| 开发与部署 | **DSH 本地开发验证**；成熟后才考虑广州 Linux Docker；严格控制常驻资源 |
| 后续方向 | 可成长为云 Mira，但 V1 不承诺多 Agent 编排、通用网关或生态市场 |

## 3. 典型用户旅程

### 3.1 定时研究

管理员登录 Mira Cloud Account，从服务中心进入 Agent 控制台，选择研究目标、提示词/任务说明、时区和日程、交付目标及运行限制。Agent 到点启动，搜索/读取资料并形成有来源的报告，送达配置的一个或多个飞书接收方。控制台能看到该次执行的开始/结束、结果、错误、取消和后续重试。

示例方向为《见π》素材发现、《气数》资料研究或用户自定义市场/科技课题；**示例并不意味着内置这些内容或默许自动发布**。资料筛选与写稿/发布是独立授权动作。

### 3.2 飞书 / 企业微信双向对话（2026-11-05 权限决策）

- 私聊：任何能在 IM 平台向机器人发送消息的人都可以正常聊天、提问与使用明确公开的能力，无需 Cloud Pi 用户白名单，也不要求是某个群的成员。
- 群聊：机器人加入的群中，任何成员明确 **@机器人**都可以交互；不设置 Cloud Pi 群 ID 白名单或群成员白名单。非 @ 消息不触发模型，群 @ 必须通过可靠的频道事件/文本判定，不把普通聊天文本当作可信身份声明。
- 会话与任务：私聊、群聊与管理员计划任务的上下文、成果和状态隔离；不能把个人数据默认发到群。群消息本身是不可信输入。
- **独立工具授权**：用户能聊天并不代表能访问维护者 Cloud Account、私有 Guanlan consumer、模型密钥、管理员任务或敏感 MCP 工具。公开聊天仅获得公开且受限的工具能力；私有读取、写操作和管理员操作必须以可信身份/明确委托独立核验，缺乏隔离实现时宁可禁用相关工具，也不恢复聊天白名单作为权限替代。
- **运营保护**：允许面向所有用户设置全局并发、超时、频率、模型预算等资源限制；这些是防滥用和成本约束，不是特定用户的准入白名单。

### 3.3 观澜消费

Agent 用账户已授权的稳定 consumer 阅读观澜候选：读取新闻索引、按需追原文、判断研究价值、形成交付。观澜拥有来源采集、身份下的新闻可见性和消费状态账本；Agent 不复制新闻采集系统，也不能凭读请求标记状态。

现阶段观澜只读 MCP 已有测试实现；消费状态写回的领域层存在，但**正式 MCP 写工具、Cloud Auth 的 Agent 委托签发及真实生产联调尚未交付**。V1 目标不等于这些链路已上线。

## 4. 控制台最小信息架构

控制台由 Cloud Auth 统一登录与服务入口承载，业务数据由 Cloud Agent 拥有，不在 Cloud Auth 中复制任务和私有对话。

| 页面/区块 | 需要呈现 |
| --- | --- |
| 总览 | Agent 状态、运行中的工作、最近失败、简单用量与成本 |
| 定时任务 | 名称、目标、日程/时区、开关、立即执行、投递对象、最近运行 |
| 运行记录 | 状态、开始/结束、耗时、失败原因、报告、来源与是否已投递 |
| 模型 | 配置供应商、OpenAI-compatible API / New API 的 baseURL/模型、成本限制；密钥服务端保管 |
| IM 连接 | 飞书/企业微信连接状态、平台可达性、投递对象、机器人平台权限；不维护聊天用户/群白名单 |
| MCP | 内建服务连接、可信第三方 server 的启停、可用工具、授权/错误状态 |
| 基本策略 | 超时、并发、速率/预算上限、取消与失败提示 |

**V1 不要求**用飞书聊天自然语言创建/修改 Cron；不要因此引入第二套任务配置源。UI 路由、部署拆分和数据表未冻结，见架构设计。

## 5. 任务与消息行为原则

- 调度器只负责可靠触发，不代替 Agent 分析；任务有稳定 ID，执行实例可区分、可追查。
- 同一计划可能发生重试/超时/重启。重复触发和通知必须可识别，避免成果重复发给同一接收方。
- 研究结果应包含来源 URL、内容与时间；失败不能伪装成“没有材料”。
- 多目标投递是业务需求，覆盖飞书和企业微信人/群；主动投递目标来自可信任务配置，不能由任意 IM 聊天消息更改。
- 预算、并发、运行时长均需要限制和可观测，不为了“长期运行”常驻大量空闲会话。
- 不主动替用户发布博客、修改观澜订阅或执行其他外部副作用；这些动作需要各自的明确授权。

## 6. 不做什么

- **不做** DC/Windows Server 远程控制、管理 Docker 集群、复制 Mira Desktop。
- **不做** MCP Gateway、集中工具市场、MCP 服务发现数据库、事件总线、分布式 Agent 编排或新用户账号系统。
- **不做** 观澜的 Feed 采集、新闻索引或 CAS 消费账本的重复实现。
- **不做** 首期全自动群聊参与、群成员管理员权限、由模型指令自行授权。
- **不做** 把所有工具描述永久加入模型上下文，也不默认批准任意 stdio 命令或未知 MCP 服务器。
- **不做** 本地 POC 尚未通过就承诺生产性能/费用或部署日期。

## 7. 阶段与验收主线

- **P0 · MCP 只读协议集成**：真实 Pi SDK Session ↔ 隔离 Guanlan workerd/D1；详见 [P0 方案](engineering/p0-mcp-poc.md)。不做飞书/调度/用户登录。
- **随后 · Agent 可工作闭环**：Pi 执行一项定时研究、保存结果、成功/失败可观察；验证飞书和企业微信的开放私聊、任意成员群 @ 及多目标投递；分别验证公开聊天不能读取私有工具数据。开发先本地。
- **随后 · Cloud Auth 控制台**：服务入口、配置/权限、执行历史与限制；实现云端无人值守委托合同后接入真实观澜。
- **生产评估**：实际测 CPU、内存、存储、模型费用及网络可达性；有回滚/备份和验收证据后才部署广州 Docker。

以上是按价值划分的阶段，并非已授权的 Issue、承诺日期或固定工期。每次施工以当时实际代码和单张 Issue 合同为准。
