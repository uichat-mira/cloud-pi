# ADR-001 · 企业微信 Channel 传输形态：长连接

> **状态：提议（Proposed），待维护者裁决。** 本 ADR 不是"已采纳"或"已实现"。
> 依据：[研究 transport.md](../research/wecom-channel/transport.md)（官方文档 62131/62132/62154 与
> 本机实验，访问日期 2026-11-04）。
> 关联：[WeCom Channel 架构](../architecture/wecom-channel.md)、[ADR-002 身份](ADR-002-wecom-identity.md)。

## 1. 背景

Cloud Pi 需要一个能在真实企业微信里收发消息的 Channel。企业微信智能机器人的 API 模式提供两种
连接方式，且**二选一**：

| | 长连接（WebSocket） | URL 回调（Webhook） |
| --- | --- | --- |
| 端点/入口 | `wss://openws.work.weixin.qq.com` | 公网 HTTPS URL |
| 加解密 | 无（明文 JSON over WSS） | Token + EncodingAESKey + 签名 |
| 部署要求 | 可内网，**无需公网 IP** | 公网入口 + 1 s 验证 + 5 s 响应窗口 |
| 高可用 | 单机器人**仅 1 条**连接 | 支持多实例负载均衡 |
| 流式 | 开发者主动推帧 | 企业微信轮询回调 URL |

环境事实：本机是 **Windows 家庭网络，没有公网入口**（无固定公网 IP、无入站端口映射、无备案域名）。
产品目标要求"真实企业微信收发 + 真实模型 + Scheduler 主动投递"，但没有要求多实例水平扩展。

## 2. 决策

**采用长连接**：`@wecom/aibot-node-sdk@1.0.7`（精确版本）连接
`wss://openws.work.weixin.qq.com`，`BotID` + `Secret` 订阅，30 s 心跳，指数退避重连，
单实例运行（主备切换，不并行）。

关键实现约束（来自研究，非本 ADR 新造）：

1. **每机器人只允许 1 条有效连接**：新连接订阅成功会踢掉旧连接（`disconnected_event`）。
2. `disconnected_event` 后 SDK **不自动重连**，由应用决定；手动 `disconnect()` 才是干净退出。
3. 协议层每帧回执超时 **5 s 且硬编码**（SDK），业务层窗口另算（欢迎语/卡片 5 s、回复 24 h、流式 10 min）。
4. 媒体 `msg_item`（图文混排）在长连接回复中**未列入文档支持**，不要依赖。
5. 版本必须钉死：仓库与 npm 版本漂移、25 个未处理 issue（研究 `sdk.md` §1）。

## 3. 后果

**正面**

- 不需要公网 IP / 域名 / 备案 / 隧道；本机开发即可验证真实链路。
- 无加解密代码：没有 Token/AESKey 的轮换与签名实现风险（少一类安全面）。
- 原生流式，用户体验优于"等模型跑完再发一条长消息"。
- 与飞书 Channel 的部署形态同构（出站长连接），运维心智一致。

**负面 / 代价**

- **不能水平扩展**：所有消息只有一个进程在收；进程挂了就断（直到重连恢复）。
- 需要显式主备：谁持有连接、如何避免双连互踢、切换时在途消息怎么处理，官方未给机制。
- SDK 回执 5 s 硬编码 + 25 个未处理 issue，属于"能用但要盯"的依赖。
- 主备切换窗口内的主动投递会失败，需要 transport 暴露 `isConnected()` 供投递层前置检查。

## 4. 被否方案

### 4.1 URL 回调（公网 HTTPS）——被否（当前环境）

- 需要公网可达的 HTTPS 入口，并实现：URL 验证 1 s 内返回解密明文、`msg_signature` 校验、
  AES-CBC 解密、5 s 内响应、`response_url`（一次性、1 h）异步回复。
- 本机没有公网入口；引入隧道/云函数等于为一个"长连接已能解决"的问题新增一跳基础设施与信任边界。
- **不是永久否决**：它是唯一支持多实例负载均衡的形态（研究 §5 选项 C 的反面）。

### 4.2 不接入（只保留飞书）——被否（产品目标）

团队目标明确要求"能在真实企业微信里工作"，且飞书通道不退化。只做飞书不满足目标。

### 4.3 传统群机器人 Webhook——被否（能力不足）

只能向群推送，**不能接收消息**，没有单聊/事件/身份（研究 `capabilities.md` §1）。无法作为 Channel。

### 4.4 自建应用（`access_token` + 应用消息）——被否（权限面与语义）

自建应用是另一套凭证体系（corpid + secret 换 `access_token`，需要可见范围/IP 白名单），
没有 AI 对话与 `req_id` 回复语义；它在本项目里只有一处合法用途——`open_userid → userid`
转换（且首版不做，见 ADR-002）。

> 另：旧文档 `path/60904` 描述的"智能机器人长连接"端点 `wss://open.work.weixin.qq.com/ws/aibot`
> 已 **404**，命令字也与现行不一致。它不是"被否方案"，而是**不可用资料**，不得作为实现依据。

## 5. 撤销/重评条件

出现任一条即重新评估本 ADR：

1. **需要多实例水平扩展**（例如并发消息量或可用性要求超过单实例主备）→ 重新评估 URL 回调
   （它支持多实例负载均衡），并同时评估隧道/云函数的运维代价。
2. **官方宣布长连接下线或改变协议**（端点、订阅帧、命令字变更）→ 以官方迁移公告为准。
3. **SDK 无法继续使用**（长期无维护、Node 版本不兼容、出现未修复的高危缺陷）且无官方替代 →
   评估自行实现协议帧（风险更高）或转 URL 回调。
4. **安全策略禁止出站长连接**（例如部署环境只允许入站 HTTPS）→ 转 URL 回调。
5. **单连接约束与产品的高可用目标冲突**（例如要求 99.9% 且不能人工切换）→ 重评。

## 6. 若将来"必须公网回调"：两种落地选项与代价（本分支当前**未触发**）

任务要求：若研究结论是"必须公网 HTTPS 回调"，给出两种落地选项与代价并标"待维护者裁决"。
**本研究结论不是这样**（长连接可用且本机已实测可达），因此本分支**未触发**，也不存在需要
立即上报 lead 的阻塞。以下仅作为未来重评时的输入（详细代价见
[transport.md §5](../research/wecom-channel/transport.md)）：

| 选项 | 做法 | 主要代价 |
| --- | --- | --- |
| A. 自建隧道 | cloudflared / frp 把本机端口映射为公网 HTTPS | 第三方/自建中转依赖；域名变化需回控制台改配置并重验；家庭宽带上行抖动会打穿 1 s 验证与 5 s 响应窗口；公网暴露面扩大 |
| B. 云函数中转 | 云函数收回调、验签解密、转发到本机 | 云账号与部署运维、出网与密钥托管、第二跳延迟与新的信任边界 |

两者都必须配合：`Token`/`EncodingAESKey` 管理、回调 URL 变更流程、多实例部署。
若真要走这条，需单独立项并由维护者裁决，**不得默认隧道可用**。

## 7. 开放问题

1. 主备如何选主（人工切换 / 外部探活 / 租约）？官方只说"建议主备"。
2. 被踢下线后，在途的流式回复如何收尾（直接失败 vs 补发一次）？
3. 是否把 SDK 的 `wsOptions` 用于固定 TLS 选项（企业代理/自签证书场景）？
4. 版本升级策略：1.0.x 无兼容声明，是否每次升级都要求重跑流式/长文/媒体 Live？
